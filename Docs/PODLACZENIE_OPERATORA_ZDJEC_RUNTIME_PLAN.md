# Podłączenie operatora zdjęć do Runtime — CK-05d.2d.3b

Plan przed implementacją po ekranie3a. Usługi i normalny adapter pozostają wyłączone/bez przełączenia. Wykonywać dopiero po lokalnym odbiorze i push3a.

1. GatewayDevelopmentRuntime: własne avatarReportReviewJournal/host/client/Keychain, słaby relay i callback do avatars.observeModeration. ClearServices, otwieranie community oraz innych paneli i nadrzędne zmiany auth/foreground/parent muszą odciąć nowy host. Nowy panel ma dokładny parent route lifetime, pojedynczy current handle i przygotowanie zamykające mapę/czat/inne panele.
2. Bootstrap zdjęć: przed jakimkolwiek oczekiwaniem zamknąć poprzednią prezentację community. Odczytać w kolejności oba journale w exact native/private/origin scope, sprawdzić scope/lifetime/cancellation po każdym await i dopiero utworzyć nowy domain/bind z dwoma pending. Błąd dowolnego peek nie może pozostawić starego odczytu lub utworzyć nowego. W aktualnym kodzie openCommunity invaliduje poprzedni domain dopiero przez community.open po peek; nowy punkt ma jednoznacznie odcinać go przed IO.
3. Mały GatewayCommunityBootstrap w pakiecie ma obsługiwać wyłącznie dwa peek i retained opening slot; zwraca dwa metadata intents oraz uchwyt lifetime, bez tworzenia domain/sieci. Runtime zamyka domain przed wywołaniem, a relay i Root invalidują jego nonce. Testy obejmą każdy błąd peek, zmianę scope po każdym await, tło/rodzica i odmowę drugiego otwarcia do końca zależności. Otwarcie ma własny nonce/lifetime: invalidation podczas peek (tło, rodzic, auth, inny panel) nie może po powrocie native wartości ponownie otworzyć community. Utrzymać opening slot do końca dependency. Przygotować lokalnie testowalny fragment bootstrapu/lifetime i syntetyczne kontrole obu peek/error/late scope; nie uznawać samej kompilacji za rzeczywisty odbiór Runtime/SIWA.
4. Account deletion: invalidate nowego hosta i fence jego journala przed usuwaniem uprawnień; obsłużyć accountID=nil dla binding i dokładne owner erasure wszystkich origin. Nie usuwać innego namespace/owner. Niepewny cleanup zachowuje odcięcie i wymaga retry zgodnie z dotychczasowym kontraktem.
5. Rzeczywisty app-hosted Security: nowa kontrola w GatewayStorageCheck,3 wyłącznie losowe syntetyczne scopes/dwóch owners, hide_photo SavedIntent utworzony przez natywną walidację lokalnej syntetycznej ramki JPEG, bez sieci/Apple/Firebase/GPS/Muzyki/profilu. Prepared/dispatched/notApplied/retiring/reopen/retired/ACK, WhenUnlockedThisDeviceOnly/noSync/4096B i dokładne erasure z pozostawieniem obcego syntetycznego owner. Cleanup i kontrola nieobecności wyłącznie własnych nowych scope. Nie czytać dawnych scope/danych.
6. Bieżący aggregate test Keychain ma propagować wynik nowej kontroli zamiast ignorować błąd. Dodać czytelny wynik diagnostyki, bez wypisywania tokenów/payloadu/nativeID/atrybutów. To lokalny Security roundtrip w symulatorze, nie fizyczne szyfrowanie lub CloudKit A/B.
7. Build przed kolejnymi callsites, odpowiednie testy bootstrap/lifetime/deletion i UI/root/regresje oraz Debug/Release/strict. Obejrzeć końcowe zrzuty. Zaktualizować plan/dziennik/dowody i commit/push; projekt użytkownika zachowany.

Po tym nadal rzeczywiste SIWA, CloudKit Development query/ASSET/CDN i nowy schemat po konkretnym przygotowaniu/zgodzie, dwa zwykłe konta A/B, Free/hosting/alarmy/limity i urządzenia oraz dopiero przełączenie adaptera/przygotowanie TestFlight. Brak nowych usług, uprawnień, sekretów lub opłat w tej lokalnej integracji. Nie ponawiamy wygasłych prób SDK lub zdalnych operacji.
