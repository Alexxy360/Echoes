# CK-04e.3h.2 — świeża autoryzacja i uchwyty zdjęć

`GatewayAvatarClient` łączy natywne źródło tożsamości, [chroniony HTTP](NATYWNY_TRANSPORT_AVATAROW.md), [cache odbiorcy](NATYWNY_CACHE_AVATAROW.md) i ImageIO. Wymaga jawnej aktywacji, zgodnego origin i konfiguracji CloudKit Development oraz obowiązkowego predykatu aktualnej widoczności wybranej wersji. Nie ma domyślnego allow-all. `GatewaySignInHost` udostępnia wymagany GatewayAvatarAuthorizationSource przez istniejące metody; nie dodano drugiego logowania ani odczytu prywatnego profilu.

To gotowy lokalny sterownik przed kompozycją serwerowej trasy, wersji zdjęć w profilu/feed i UI. Zwykła aplikacja nadal Firebase, aktywacje wyłączone. Runtime nie tworzy pozornie działającego klienta z pustym predykatem i nie wysyła żądań do diagnostycznego Workera. Nadal wymagane są serwerowy admission/HTTP, upload/journal/UI/operator/retencja oraz rzeczywisty odbiór Development/Free/A-B.

## Przebieg jednego wyświetlenia

1. `connect` wiąże snapshot konta/binding/revision z aktualnym PrivateAccountScope, konfiguracją gateway i nowym lease cache. Ponownie kontroluje tożsamość po aktywacji lease i odczycie tokenu. Nie zachowuje tokenu w kliencie. Niedokończony connect zajmuje swój slot do zwrotu i fence starego lease; invalidacja nie pozwala równoległemu connect wyprzedzić późnego acquire.
2. `load` przyjmuje wyłącznie reference, wariant i opcjonalne współrzędne. Nie przyjmuje hasha od widoku. Nowa próba usuwa wcześniejsze uchwyty tego wariantu i unieważnia starsze zadanie tego wyboru, także przy odmowie przez backpressure. Nowa wersja odcina wszystkie warianty poprzedniej wersji właściciela.
3. Odczyt cache jest tylko kandydatem. Sterownik jeszcze raz sprawdza reference/wariant/rozmiar i dekoduje ImageIO. Dopiero zweryfikowany kandydat może dostarczyć knownSHA256. Błędny kandydat prowadzi do świeżego pobrania bez jego hasha.
4. Każde load ponownie pobiera token z natywnego źródła i wykonuje serwerowy read. Nie korzysta z wcześniejszego uchwytu lub stanu sukcesu jako zgody. Odpowiedź 204 musi pasować do całego manifestu i zweryfikowanego kandydata. Odpowiedź 200 wymaga zgodnego wyboru i ImageIO; dopiero wtedy może trafić do cache i prezentacji.
5. Po każdym await — cache, dekoderze, tokenie, HTTP i zapisie — kontrolowane są kontekst/revision, prywatne konto iCloud, aktywacja, epoki widoczności i wersji, aktualny predykat oraz czas żądania. NativeGatewayAvatarDecoder wykonuje ImageIO w Task.detached, przenosi anulowanie do dziecka i sprawdza je przed rozpoczęciem oraz po zwrocie. Trwający synchroniczny ImageIO nie jest przerywany w połowie.

Błąd odczytu lub zapisu opcjonalnego cache nie blokuje świeżego, poprawnego obrazu z sieci. Utrata lease zamyka cały kontekst. Odmowa/błąd serwera usuwa wcześniejsze obrazy właściciela; brak sieci nie daje offline fallback. Cofnięta sesja zamyka lokalny kontekst i odrzuca tylko pasujący snapshot natywny. Spóźnione 401 konta A nie może odrzucić konta B. Nieznane błędy zależności są zamieniane na zamknięty komunikat, bez przekazania surowych szczegółów do UI.

## Uchwyt, obserwacja i pamięć

Wynikiem jest `GatewayAvatarPresentation` z prywatnym losowym ID, zredagowanym opisem/Mirror i bez CGImage, bajtów, współrzędnych lub tokenu. Widok musi przechowywać uchwyt i rozwiązywać go przez `image(for:)` bieżącego klienta. Getter sprawdza aktualny natywny kontekst, widoczność, epoki i czas. Odczytuje observable presentationRevision, a także observable stan źródła/predykatu. Zmiana konta, tła lub lokalnej widoczności odcina render; host musi dodatkowo synchronicznie wywołać invalidate/invalidateVisibility/invalidate(ownerID:) przy właściwych zdarzeniach. Same powroty predykatu false→true nie zastępują epoki ABA.

Uchwyt jest ważny najwyżej 30 s od rozpoczęcia żądania, według monotonicznego systemUptime. Późny serwer nie odnawia tego czasu. Zadanie wygaśnięcia usuwa piksele z pamięci i publikuje zmianę nawet bez kolejnego wywołania gettera; planuje kolejny termin dla pozostałych obrazów. Niepoprawny zegar nie tworzy nieprawidłowego Duration. To krótkie okno lokalnej prezentacji, nie obietnica natychmiastowego odwołania bajtów już dostarczonych odbiorcy.

Sterownik ma najwyżej cztery load w toku, 32 obrazy i 8 MiB sumy bytesPerRow×height przechowywanych CGImage. Usuwa najstarsze prezentacje, zanim przekroczy limit. To limit zarządzanych rastrów, nie pomiar RSS, buforów ImageIO/systemu ani kopii zachowanych przez widok. Invalidation anuluje zadania, ale nie usuwa niezakończonych slotów: dostawca ignorujący cancel nie tworzy nieograniczonego backlogu. Zamknięte konteksty nie mogą publikować jego późnego wyniku. Faktyczne zakończenie transportu opiera się również na timeout URLSession; sam predykat deadline nie przerywa dowolnej zależności, która nigdy nie zwróci.

Host musi utrzymywać jeden współdzielony foreground client oraz cache, odcinać zdarzenia natywne/domain/obszaru/blokad/wybranej wersji i nie zachowywać CGImage poza ważnością uchwytu. Sterownik nie uruchamia samoczynnie HTTP po wygaśnięciu. Przyszły UI ma planować odświeżanie tylko potrzebnych widocznych treści, uwzględniając liczbę RPC i odbiór Free; nie zakładamy darmowego dowolnego ruchu. Uprawniony odbiorca może skopiować już otrzymane piksele — uchwyt tego nie uniemożliwia. Predykat i źródło są zaufanymi zależnościami aplikacji, nie kryptograficzną granicą wobec zmodyfikowanego klienta.

## Weryfikacja i pozostały odbiór

Testy obejmują całe lokalne przejście fixture rzeczywistego serwerowego readera przez GatewayAvatarHTTPClient, trwały cache, NativeGatewayAvatarDecoder i ImageIO. Oddzielne bramki modeli zatrzymują operacje podczas cache/token/HTTP/decode/store, również ignorując cancel. Sprawdzono nowe konto iCloud przy tym samym snapshot gateway, zmianę natywnej revision i wersji zdjęcia, ABA widoczności, późne 401 A po aktywacji B, bounded backlog i pamięć 32/8 MiB oraz automatyczne wygaśnięcie/reschedule z rzeczywistym zegarem. Kontrola negatywna bez porównania PrivateAccountScope musi oblać test i wykazuje niepożądany zapis. [Wyniki i hashe](evidence/avatar-native-client-local-tests.json).

Modele kont/sesji/API nie są rzeczywistym logowaniem Apple, zdalnym CloudKit lub odbiorem ról dwóch zwykłych kont. Nadal otwarte: fizyczne FileProtection.complete i blokada telefonu, realne hosty assetów/schema/role/SIWA/Free/A-B, serwerowy HTTP/admission i wskazania wersji, uploader/journal/UI, moderator/oglądanie/zgłaszanie zdjęć, kontakt i retencja oraz cały pozostały plan migracji. Nie aktywowano usług, kluczy lub opłat, nie zmieniono Production/Firebase i nie zainstalowano nowej wersji na telefonie.


Aktualizacja CK-04e.3i.3a: [współdzielony host](HOST_ZDJEC_SPOLECZNOSCIOWYCH.md) jest tworzony w kontrolowanym Runtime i przekazuje AppServices binding z lease odbiorców. Obejmuje synchroniczne granice Core/pending block i wspólny limit niezakończonej pracy przez rebind. Widoki/renderer jeszcze nie korzystają z tego bindingu; następny CK-04e.3i.3b. Nie zmienia to potrzeby świeżego odczytu, kontroli przy renderze i odcinania natywnej tożsamości.
