# R-04c.1 — pierwsza rzeczywista próba logowania: przygotowanie

Plan zapisany 21 listopada 2026 przed zmianą ekranu. R-04b jest wdrożony i wyłączony; to nie jest jeszcze zgoda na aktywację, przekazanie sekretów lub instalację. [Wynik konfiguracji](APPLE_I_HOSTING_WYNIK_DEVELOPMENT.md).

1. Dodać wyłącznie w istniejącym ekranie Debug wariant próby uwierzytelnienia, wybierany z zaufanego Info.plist (`EchoesGatewayAuthenticationTrial=true`). Ukryć wejścia do mapy/czatu/profilu/moderacji/usuwania oraz odciąć ich programową nawigację. Zachować rzeczywisty GatewayDevelopmentRuntime, natywny arkusz, Keychain i klient HTTP. Bez nowego endpointu, imitacji erasure lub testowego sukcesu OAuth.
2. Pokazać identyfikator nowego konta testowego dopiero po faktycznym sukcesie logowania. W tym wariancie wypisać do lokalnej konsoli jedynie ten sam zwalidowany UUID z jednoznacznym prefiksem; służy powiązaniu późniejszego SQL cleanup z kontem potwierdzonym przez telefon. Nie logować Apple user ID, tokenu/code/nonce, pary sesji, pól profilu lub Keychain. Identyfikator testu pozostaje poza publicznym Git.
3. Przygotować nieaktywny szablon Info.plist z dokładnym origin `https://echoes-community-development.2rnd2bt6rd.workers.dev`, kontenerem Development i wyłączoną aktywacją. Zbudować Debug Simulator i unsigned Release oraz ponowić istniejącą kontrolę odmowy bez aktywacji. Nie instalować na telefonie ani nie uruchamiać rzeczywistej autoryzacji.
4. Po gotowym kodzie i dowodach przygotować jeden konkretny zakres: tymczasowy token wdrożenia wyłącznie tej usługi; przekazanie SIWA QPBMSAY553 i trzech niezależnych kluczy vault/renewal/HMAC jako sekretów Cloudflare; aktywacja tylko auth w jednym oknie do45min, nowy profil/podpis Debug oraz instalacja na dotychczasowym iPhonie15Pro. PublicRecords/Community/Deletion/Avatar pozostają0, bez klucza CloudKit w Cloudflare. Właściciel sam potwierdza arkusz Apple/FaceID. Jeszcze nie wykonywać tych kroków.
5. Najwyżej jedno nowe interaktywne logowanie. Sprawdzić rzeczywisty code exchange, zapis sesji, zimny restart i odtworzenie, następnie po prawdziwym wygaśnięciu dostępu ponowny restart/rotację renewal oraz jawne logout-all. Kod ma dostęp do10min i kontrolę Apple po24h: rotacja w tej krótkiej próbie **nie jest** testem serwerowego refresh u Apple. Nie przestawiać zegara lub skracać polityki dla uzyskania zielonego wyniku.
6. Przed cleanup zatrzymać klienta i wyłączyć publiczną trasę/aktywację. Właściciel odwołuje zgodę Apple dla testowego Echoes; jego potwierdzenie oznaczyć jako czynność właściciela, nie jako dowód serwerowego OAuth revoke. Usunąć wyłącznie wiersze konta odpowiadającego UUID z telefonu, jego własne sesje/grants/zaszyfrowane credentials/rezerwacje i lokalny wpis sesji. Nie ujawniać wartości tokenów w SQL/raporcie; najpierw dokładny inwentarz nazw/ilości i sprawdzenie właściciela. Nie kasować całego namespace ani innych kont. Jeżeli pojawi się inne konto lub niepewne IO, zatrzymać mutacje i zachować informację o pending, bez udawania sprzątnięcia.
7. Zgoda na ten przebieg musi uwzględniać trwałe powierzenie istniejącego klucza SIWA QPBMSAY553 usługodawcy Cloudflare. Po próbie wyłączyć HTTP i usunąć sekrety z aktywnej wersji oraz token wdrożenia; historyczne wersje/PITR mogą zachować kopie i nie obiecywać ich fizycznego wymazania. Zachować dotychczasowy klucz zarejestrowany w Apple do dalszej migracji. Nie tworzyć ani nie unieważniać kluczy przy każdej próbie; zmianę tego trwałego uprawnienia przygotować osobno, gdy będzie potrzebna. Okno45min dotyczy aktywnego testu usługi, nie czasu posiadania kopii klucza przez Cloudflare.
8. Raport ma oddzielić: native login/code exchange/session/renewal/logout, czynność ręczną Apple i niezaliczone serwerowe refresh/revoke. R-04 jako całość, A/B, query/ASSET, retencja/usuwanie/PITR i pełny klient nadal muszą przejść odbiór. Nie przełączać zwykłego AppServices ani nie usuwać Firebase w tym etapie.
