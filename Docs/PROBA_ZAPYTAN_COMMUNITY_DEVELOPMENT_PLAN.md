# Ograniczona próba zapytań CloudKit — R-02

Plan zapisany21listopada2026 przed implementacją harnessu. Wykonywać lokalne przygotowanie niezależnie od oczekiwania na R-01; typy presence/message istnieją w potwierdzonym świeżym eksporcie. **Ten plan nie upoważnia do sieci, tworzenia rekordów lub ponowienia dawnej próby8rekordów.**

1. Przygotować czysty deterministyczny inwentarz12nowych rekordów:6presence/6message, wyłącznie losowe identyfikatory, syntetyczny tekst i stałe współrzędne bez GPS. Własne ID/owner/request/recordSortKey wynikają z losowego runID. Obejmować kilka pasujących rekordów (także równe daty), daleki rekord, wygasły rekord oraz inactive presence/future message. Związać kanoniczny plan z SHA i świeżym schematem. Żadnego checkpointu, prywatnego profilu, zdjęcia/ASSET lub istniejącego konta użytkownika.
2. Budować zamknięte query zgodne z produkcyjnymi filtrami lokalizacji/czasu/active/erased i sortowaniem daty/recordSortKey, ale z dodatkowym warunkiem do dokładnie własnych recordNames. Apple opisuje `systemFieldName: recordName`, referencje i `IN`; zanim zaplanowane zostanie wykonanie, payload ma przejść lokalne testy i osobną walidację zakresu w transporcie. Żadne szerokie query całego typu. Wyniki wyłącznie minimalne metadata, każdy nieznanyID zamyka próbę.
3. Wariant resultsLimit2 ma wymusić rzeczywistą continuation i walidację kolejności/duplikatów/postępu. To odbiór ograniczonego wariantu query i indeksów, nie pełnej pojemności25/page, scenariusza ponad100wiadomości, egzekwowania3km przez zmodyfikowanego klienta ani dwóch zwykłych kont. Te wymagania pozostają w dalszym odbiorze pełnego Runtime.
4. Przed siecią utrwalić prywatny inwentarz i journal. Prepare/inspect bez sieci; run wymaga nowego opt-in i permit z dokładnym SHA, istniejącym keyID/SPKI, jedną rezerwacją okna do30min i maksymalnie32wywołaniami. Limit obejmuje preflight/create/query/lookup/delete i sprawdzenie nieobecności. Ograniczyć batch/body/deadline, zatrzymać cofnięcie wall/monotonic, cancel/timeout i zachować slot do rzeczywistego zakończenia IO. Błąd nie inicjuje automatycznej drugiej próby.
5. Preflight dokładnych ID musi potwierdzić nieobecność; kolizja bez zapisu. Create najwyżej raz. Cleanup po świeżym tagu wyłącznie potwierdzonych własnych rekordów, z exact lookup i trwałą informacją o niepewnym wyniku. Nie force-delete, nie query-delete, nie przejęcie istniejącego rekordu. Po utracie okna przygotować konkretny zakres samego sprzątania, bez ponownego create lub query. Nie adaptować starego wyczerpanego permitu.
6. W miarę możliwości reużyć istniejące podpisywanie Development i prywatne operacje plikowe, zachowując zamknięte kontrakty starego8rekordowego harnessu. Nowy query contract i journal mają pozostać odrębne; nie rozszerzać działającego endpointu lub publicznego RPC dla diagnostyki. Klucz lokalny poza Git/aplikacją/Cloudflare, brak nowych praw lub sekretów.
7. Sprawdzić plan/payloady, brak dowolnego query/ID/URL, kolizję, zły/obcy/powtórzony wynik, continuation/cykl, awarie tworzenia/IO/cleanup/restart i odmowę domyślnej sieci. Użyć dwóch wspieranych Node; nie przedstawiać modelu CloudKit jako odbioru jego planner/indexów. Następnie przygotować konkretny prywatny inwentarz, zakres i przetestowany CLI do osobnej zgody przed run.

Źródła: [query i mapowanie systemFieldName](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/CloudKitWebServicesReference/QueryingRecords.html), [filtry/IN/referencje](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/CloudKitWebServicesReference/Types.html). Indeksy są aktualizowane asynchronicznie: wynik niepełny lub brak indeksu nie jest zgodą na zdjęcie filtrów. Zakończyć niezaliczeniem, zachować własny cleanup i przygotować konkretny następny krok.
