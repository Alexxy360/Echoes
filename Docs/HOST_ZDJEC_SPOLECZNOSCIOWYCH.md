# CK-04e.3i.3a — współdzielony host zdjęć społecznościowych

Kontrolowany GatewayDevelopmentRuntime tworzy jeden GatewayCommunityAvatarHost ze wspólnym klientem i cache. Każda prezentacja społecznościowa otrzymuje oddzielne powiązanie z CommunitySession i aktualną tożsamością natywną/prywatną. AppServices przechowuje to powiązanie i odcina je synchronicznie podczas invalidateNativePresentation. Stare powiązanie nie może wyczyścić ani odczytać nowej prezentacji. Standardowe AppServices ma avatars=nil; aktywacje usług pozostają wyłączone.

Widok będzie rejestrował lease dla referencji i zamkniętej powierzchni: mapa, profil osoby z mapy lub konkretna wiadomość. Lease nie zawiera pikseli ani uprawnień serwera. Host dopuszcza do 320 odbiorców i sprawdza ich aktualny rekord rodzica przy rejestracji oraz każdym renderze. Potrzebne są gotowa sesja, foreground, bieżące powiązanie natywne/prywatne i użyteczny obszar. Dla mapy/profilu dodatkowo aktualny rekord w odległości do 3 km; dla wiadomości otwarty czat i niewygasła wiadomość. Ten host dotyczy prezentacji społecznościowej; przyszłe własne zdjęcie w ustawieniach nie jest jeszcze zaimplementowane.

Aktualne wskazanie mapy ma pierwszeństwo nad starszą wersją w wiadomościach, także gdy jest null. Bez wpisu mapy sprzeczne lub puste wskazania wiadomości nie dają zdjęcia. Każdy pozytywny odczyt pliku nadal przechodzi świeży RPC, pełny manifest i istniejące zabezpieczenia GatewayAvatarClient. Dane regionu są deklaracją klienta, nie atestacją GPS. Sygnały tożsamości muszą odcinać binding na granicy natywnego konta; Runtime używa istniejącego synchronicznego clearDomainState. Gettery ponownie sprawdzają tożsamość, ale nie zastępują tego powiadomienia przy zmianie A→B→A.

Core ma jednego słabego, wyłącznego CommunityPresentationObserver. Powiadomienia po zmianie stanu są synchroniczne, przed następnym await. Host przelicza uprawnienia po zmianie konta/foreground/obszaru/list/wersji/blokad/czatu. Core od początku próby block/unblock umieszcza autora w blockingUserIDs, zanim wywoła adapter. Cleanup nie dotyka nowej epoki konta. Utrata kwalifikacji odcina wcześniej uzyskane uchwyty i pracę w toku. Zmiana pseudonimu, utworu lub przedłużenie ważnej obecności bez zmiany wyboru nie uruchamia nowego RPC.

Równocześni odbiorcy tego samego właściciela/wersji/wariantu mogą dołączyć do oczekującej świeżej odpowiedzi. Nowy odbiorca po zakończeniu odczytu wymaga kolejnego świeżego żądania i zastępuje wspólną prezentację; stare piksele nie są fallback. Odłączenie miniatury nie usuwa oddzielnie oglądanego pełnego zdjęcia. Cztery niezakończone odczyty i jeden connect są wspólne również po ponownym bind; anulowane zależności zajmują miejsca aż do rzeczywistego powrotu. Kolejka i rejestr odbiorców są ograniczone. Zależność ignorująca anulowanie może opóźnić nowe zdjęcia; nie deklarujemy jej fizycznego zatrzymania.

Lokalny budżet hosta to do 12 odczytów/min, w tym do 4 pełnych zdjęć/min, na Runtime według monotonicznego zegara. Nie resetuje się przy bind. Nie zastępuje trwałych limitów serwera ani nie dowodzi darmowej wydajności publicznej aplikacji. Brak automatycznej pętli ponowień: błąd połączenia kończy loading, a jawny retry może wznowić pracę. Obecny limit prezentacji do 30 s i automatyczne odcięcie pikseli nie uruchamiają kolejnego RPC. Polityka odświeżania/renderowania i pomiar Free pozostają do odbioru.

## Weryfikacja i granice

Core28/28 oraz CloudKit319 zaliczonych+1 jawny skip sprzętowy na Macu i iPhone17Pro Simulator/iOS26.1. 13 nowych funkcji: 2 Core i 11 hosta. Strict swift-format8 plików; pełne Debug Simulator/Release iOS przechodzą. Testy używają rzeczywistego CoreSession, klienta/cache/Darwin filesystem i ImageIO, z modelami natywnej tożsamości/HTTP. [Wyniki i SHA](evidence/avatar-host-local-tests.json).

Testy obejmują współdzielenie oczekującego odczytu, nowego odbiorcę po zakończeniu, brak IO bez odbiorcy, wersje/null/ABA, blokadę przed ACK i świeżą autoryzację po błędzie, background/foreground, zmianę konta przy czterech zatrzymanych odczytach, rozdział wariantów, limity/320 odbiorców, expiry/czat i błąd connect. Kontrola negatywna bez bariery pending block oblała test i ujawniła nadal dostępny CGImage. Nowy test błędu połączenia najpierw wykazał wiszący loading; po poprawce przechodzi, podobnie jak pełna regresja.

Rejestrację/zwalnianie odbiorców zmieniono na przyrostową po wolnym teście 320 wpisów; focused10 funkcji spadło z około5,3s do0,18s na tym Macu. To obserwacja lokalnych modeli, nie pomiar płynności UI lub hostowanego obciążenia. Sprzętowy FileProtection pozostaje pominięty.

Renderer i rejestrowanie lease w rzeczywistych widokach są następnym CK-04e.3i.3b. Bez nich ten etap nie pokazuje jeszcze zdjęć w aplikacji i nie wykonuje ich sieciowego odczytu. Nie powtarzano niezmienionych UI testów ani SDK na telefonie. Nie zmieniono gateway, lockfile, projektu, konfiguracji, zależności i CI; nie powtarzano ich pełnych testów/audytu. Brak deploy/aktywacji, nowych usług/kluczy/sekretów/opłat i zmian Production/Firebase/TestFlight. Realne schema/role/hosty/SIWA/service identity/Free/A-B, uploader/journal/operator/zgłoszenia/retencja i reszta planu nadal otwarte.


## Uzupełnienie CK-04e.3i.3b

Widoki mapy, profilu i czatu rejestrują już lease przez [wspólny renderer](RENDERER_AVATAROW_IOS.md). Getter binding.isAvailable obserwuje rewizję i bieżące bramki operacyjne, aby montowanie przed activate nie zgubiło rejestracji. Nie zastępuje kontroli rodzica w acquire/render. Nowy test obejmuje zimną sesję, foreground, rebind i invalidate bez odzyskania starego bindingu; brak IO przed rejestracją. Końcowa regresja pakietu: 320 zaliczonych+1 sprzętowy skip na Macu i Simulatorze, 23/23 UI oraz Release. Dowód dotyczy syntetycznego podglądu, nie realnego providera lub darmowej skali. Historyczne wyniki etapu 3a powyżej pozostają bez zmian.
