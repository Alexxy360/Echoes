# R-03 — plan rzeczywistego odbioru zdjęć

21 listopada 2026. Plan przed implementacją narzędzia. R-04c.1b nadal czeka na odrębną zgodę; ten etap nie korzysta z Cloudflare ani telefonu.

1. Przygotować zamknięte lokalne narzędzie do rozpoznania hostów uploadu Apple. Dokładny losowy rekord `EchoesAvatarV1`, tylko pola `image` i `thumbnail`; jedna podpisana prośba `assets/upload` o dwa granty. Zwrócone URL-e są sekretami przejściowymi: nie otwierać ich, nie logować ani nie zapisywać. Zapisać wyłącznie zweryfikowane pełne nazwy hostów oraz przypisanie pola. Bez obrazu, `records/modify`, query lub odczytu istniejącego rekordu.
2. `prepare` i `inspect` bez sieci/klucza. `run` wymaga nowego konkretnego permitu, SHA inwentarza, istniejącego keyID/SPKI, jawnego opt-in i okna do 30 min. Przed jedynym requestem zapisać niepowtarzalną rezerwację. Brak automatycznej powtórki po timeout lub restarcie. Odpowiedź ograniczyć do 16 KiB, 64 fragmentów i 8 s; kontrolować aktualność zgody i zegar wall/monotonic. Nie używać zużytych permitów innych prób.
3. Lokalnie sprawdzić rzeczywisty podpis, dokładny request, odmowę domyślnej sieci, zły/obcy grant, przekierowanie, host/IP/userinfo/port, brak ujawnienia URL/tokenów, limit ciała, anulowanie oraz jednorazową rezerwację. Następnie przygotować jeden prywatny inwentarz i konkretny zakres do osobnej zgody. Niczego nie uruchamiać w Apple przed nią.
4. Dopiero po rzeczywistym rozpoznaniu hostów przygotować dalszy spójny test dwóch małych wariantów JPEG: normalizacja istniejącym kodekiem, manifest/SHA, grant, upload na dokładnie dozwolone hosty, przypięcie do wyłącznie własnego nowego rekordu, dokładny odczyt, CAS oraz zgodność pobranych bajtów. Nie rozszerzać listy hostów automatycznie i nie tworzyć wildcard. Ten test będzie miał odrębny inwentarz, stan niepewnych uploadów i świeży zakres zgody.
5. Pełny chroniony odczyt, wycofanie/stare uprawnienia, retencja i sprzątanie R-03 wymagają aktywnego Runtime i odbioru jego praw. Odróżnić usunięcie rekordu od fizycznej retencji Apple/CDN; nie deklarować sprzątnięcia nieprzypiętego assetu lub unieważnienia istniejącego URL bez dowodu dostawcy. Nie używać modelowanego checkpointu jako dowodu rzeczywistej ochrony.

Pierwszy krok jest przygotowaniem odbioru, nie zaliczeniem całego R-03. Istniejący kod produkcyjny `CloudKitAvatarAssets`, `CloudKitAvatarRepository` i chronione czytniki pozostają wyłączone; nie należy ich zastępować nowym endpointem diagnostycznym.

Apple opisuje oddzielnie prośbę o URL, przesłanie danych i przypięcie assetu w [Uploading Assets](https://developer.apple.com/library/archive/documentation/DataManagement/Conceptual/CloudKitWebServicesReference/UploadAssets.html). Dokumentacja określa ograniczony czas ważności URL uploadu; nie jest to dowód fizycznego usunięcia pliku po błędzie. W pierwszej próbie nie przesyłamy żadnego pliku.
